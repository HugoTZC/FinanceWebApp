# Auditoría técnica — 24 de agosto de 2026

## Resumen

El frontend Next.js es reutilizable y genera páginas estáticas. El backend Express funciona localmente y consulta Supabase a través de PostgREST con una clave `service_role`. La migración a Python puede ser incremental: Vercel Services permite publicar Next.js, FastAPI y Express juntos en un proyecto, despliegue y dominio.

No se debe publicar la API de datos a producción hasta confirmar o aplicar RLS en la base remota. El SQL versionado original crea 15 tablas en `public` sin habilitar RLS.

## Evidencia verificada

- Git: rama `main`, sincronizada con `origin/main`, con cambios locales previos preservados.
- Frontend: Next.js 16.3.2 y React 19.1; `next build` terminó correctamente y prerenderizó las 10 rutas enumeradas como contenido estático.
- Calidad frontend: el build original omitía TypeScript y lint. Se corrigió la extensión JSX de `data/transactions.ts` a `.tsx`, los errores de tipos detectados y se eliminó la omisión de TypeScript del build. `npx tsc --noEmit` pasa.
- Backend: Express escucha localmente en `:5000`; `GET /api/health` respondió correctamente.
- Pruebas backend: Jest pasa la prueba de salud (`1/1`). Express se actualizó a 5.2.1 y sus rutas se adaptaron al nuevo `path-to-regexp`.
- FastAPI: cuatro pruebas pasan, incluidas las rutas con y sin el prefijo público `/api/v2`.
- Supabase: conexión HTTPS de solo lectura confirmada. El OpenAPI remoto contiene las mismas 15 tablas y nombres de columnas que `backEnd/schema.sql`.
- RLS remoto: no confirmado porque las herramientas MCP autorizadas no aparecieron en esta tarea; la clave `service_role` no permite observar el efecto de RLS.
- Vercel: CLI 59.5.0 instalada y autenticada. `vercel.json` define tres Services bajo un solo proyecto y la CLI detectó correctamente Next.js, FastAPI y Express. No existe todavía un proyecto remoto cuyo nombre contenga `finance`.

## Riesgos encontrados

- El backend usa `service_role`, que omite RLS; cada ruta debe mantener filtrado por usuario hasta completar Supabase Auth.
- `schema.sql` no contiene `ENABLE ROW LEVEL SECURITY` ni políticas.
- La autenticación actual usa usuarios y JWT propios, no Supabase Auth.
- Había un secreto JWT codificado, logs de tokens/contraseñas y un reset token devuelto por HTTP; se retiraron del código.
- La carga de avatares escribe al sistema de archivos local. Vercel Functions tiene filesystem de solo lectura salvo `/tmp`; debe migrarse a Supabase Storage.
- El rate limit en memoria de Express no es global entre instancias serverless.
- `NEXT_PUBLIC_API_URL` local apuntaba a `localhost`; el frontend ahora usa `/api` automáticamente en producción.
- Antes de actualizar dependencias se detectaron 8 vulnerabilidades de producción en frontend (2 críticas) y 16 en backend. Tras actualizar versiones y lockfiles, `npm audit --omit=dev` reporta 0 en ambos servicios.
- Git rastreaba 8,423 archivos generados bajo `backEnd/node_modules`. Se desindexaron con autorización explícita, sin borrar los archivos locales; backend y frontend quedan cubiertos por sus reglas de `.gitignore`.

## Bloqueos para producción

1. Confirmar/aplicar RLS y ejecutar Supabase Database Advisors.
2. Configurar en Vercel los secretos server-side listados en el README.
3. Ejecutar un Preview Deployment Linux con los tres servicios. La CLI detecta la topología, pero `vercel dev -L` 59.5.0 en este Windows genera `vc_init_dev.py` con una ruta `C:\Users...` sin escapar y FastAPI cae antes de enlazar el puerto.
4. Migrar avatares a Supabase Storage o deshabilitar temporalmente esa función en Vercel.

## Ruta incremental

1. Publicar FastAPI bajo `/api/v2` y mantener Express bajo `/api`.
2. Migrar primero health, cálculos y endpoints de lectura.
3. Adoptar Supabase Auth y políticas RLS vinculadas con `auth.uid()`.
4. Migrar escrituras por dominio (transacciones, cuentas, tarjetas y ahorros).
5. Retirar Express cuando el contrato de rutas y las pruebas de regresión estén cubiertos.
